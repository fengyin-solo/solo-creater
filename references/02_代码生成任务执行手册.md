# 代码生成任务执行手册

## 出题目标

基于现有系统的业务背景，要求从零生成一个新功能模块。以产品需求的形式描述目标，让模型自主设计并实现完整可运行的代码。

题目读起来像产品经理在提新需求，而不是工程师在分配任务。

---

## 0-1 不等于「不受查重约束」（2026-09-16 实测）

从零生成一个新功能，确实不要求仓库里已经有对应的模块——但**平台查重规则 C 照样适用**：
它比的是「主体 + 需求模式」，不看这个功能现在存不存在。

- cc-6600009 那批 17 条 0-1 代码生成废了 10 条（59%），比功能迭代（56%）还高；
  21 对判废对里 10 对两边都是 0-1 代码生成。
- 判词原话：「同属设备监控平台按设备统计一段时间采样的分析视图，一个看位置停留热区、
  一个看电量下降速度，功能重心不同」「共同主体是生成受控只读访问入口，但一为现场扫码巡检登记、
  一为监控视图只读分享」「同在告警中心新增能力，但升级规则校验与实时新增提示功能不同」。
- 所以凭空造功能也要守两件事：**别和同批其他题落在同一个主体上，也别用同一个需求模式**
  （新增分析视图 / 受控只读入口 / 属性扩展 / 批量清单流程 / 阈值流转 / 全局显示偏好…）。
  两条新功能只要主体或模式撞了，判词里的结论就是「功能不同，照样作废」。
- 整批配比同样要守：新增能力类（0-1 代码生成 + 功能迭代）占比不超过 50%，
  把余量让给缺陷修复、重构、理解、工程化——实测后三类废弃率 0%–29%。

## 提示词质量标准

**必须包含：**
- 新功能的业务目标（解决什么问题、满足什么需求）
- 功能的核心行为描述（输入什么、输出什么、有什么规则）
- 与现有系统的关联（接在哪个环节、数据从哪来）
- 两个以上互相咬合的能力点：例如入口与可见范围、列表与详情、提交与回看、状态流转与后续操作，不能只描述一个孤立能力。
- 至少一项非开心路径：空数据、失败重试、重复提交、极端输入或耗时操作。
- 至少一项与既有行为共存的约束：已有数据、已有入口或既有流程不受影响。

**禁止包含：**
- 文件路径、类名、函数名、数据库表名
- 技术选型指令（"用 Redis 做缓存""调用 xxx API"）
- Markdown 格式（标题、粗体、列表符号、代码块）

**写法要求：**
- 默认从新增能力本身起笔，不要用"现在只有……希望新增……"把现状铺在前面。
- 不得把题目写成单页面多一个按钮、多一个独立面板这类单点新增。

**隐藏约束：**
- 允许把"刷新后仍保持当前结果""重复操作不产生重复数据"这类合理预期留在题面之外，交由验收阶段核对。
- 不允许隐藏核心能力本身：新功能做什么、面向谁、结果落在哪里必须写进题面。

**字数要求：**
- 全文不超过 250 字（空白字符不计入），约束要求融入正文，不得单独分行或加标签前缀

## 正确示例

新增待办提醒功能：对超过 3 天未处理的申请，系统每天自动给对应负责人发出站内提醒，提醒内容包含申请编号和已经等待的天数。提醒列表要支持标记已处理并显示每条的等待时长，负责人处理掉申请后对应提醒自动消失；没有任何待办时要给出空态说明，提醒发送失败时要在列表里标出可重试的条目，申请原有的提交与审批流程不受影响。

## 反面示例（禁止出现此类写法）

## 常见错误

1. 把实现细节当需求描述 → 只说"要做什么"，不说"怎么做"
2. 功能边界不清晰 → 补充触发条件、处理规则
3. 缺少与现有系统的联系 → 说明新功能接在哪个流程里
4. 超过 250 字 → 合并重复表达，保留核心业务逻辑与必要约束
