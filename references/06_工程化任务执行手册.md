# 工程化任务执行手册

## 出题目标

围绕构建流程、自动化、CI/CD、测试配置、依赖管理等工程效率问题出题，描述团队在开发流程中遇到的痛点，让模型提供可落地的工程化方案。

题目读起来像团队负责人在解决开发效率问题，而不是工具文档说明。

---

## 提示词质量标准

**必须包含：**
- 当前工程流程中的痛点（手动操作、配置混乱、发布风险等）
- 期望达到的改进效果（自动化、标准化、减少人为错误等）
- 与现有技术栈/流程的兼容性要求
- 至少两个被这条流程串起来的环节，说明改造后各环节如何衔接。
- 至少一项失败可见性要求：不通过或中途失败时，要能看出是哪一步、什么原因。

**禁止包含：**
- 文件路径、配置文件名、脚本名称
- 具体工具命令（"用 GitHub Actions""写 Makefile target"）
- Markdown 格式

**隐藏约束：**
- 允许把"重复执行不会污染产物""失败后可以重跑而不留残留"这类合理预期留在题面之外，交由验收阶段核对。
- 不允许隐藏痛点本身：现在卡在哪一步、希望流程变成什么样必须写进题面。

**字数要求：**
- 全文不超过 250 字（空白字符不计入），约束要求融入正文，不得单独分行或加标签前缀

---

## 正确示例

每次发布新版本都需要人工检查依赖版本、手动跑测试、手动打包，步骤多容易遗漏，不同人操作结果也不一样。希望把检查和构建串成一条自动流程，发布前自动完成；任何一步不通过时能看出是哪一步、什么原因，修好后可以重新执行，不会残留上次失败的中间产物。

---

## 反面示例（禁止出现此类写法）

❌ 请在 .github/workflows/ 目录下创建一个 CI 流程文件，包含 lint、test、build 三个 job，在 push 到 main 分支时自动触发。

❌ 修改 Makefile，添加 release target 调用 docker build 和 docker push。

---

## 常见错误

1. 直接写出工具名或配置文件路径 → 改用"自动化流程""发布检查"等业务描述
2. 需求太抽象（"改善 CI"）→ 补充具体的流程痛点
3. 涉及业务逻辑而非工程化 → 工程化只关注流程、工具链、自动化，不涉及业务
4. 超过 250 字 → 删去背景，直接说"现状问题 + 期望效果 + 衔接关系"
