# Bug 修复任务执行手册

## 出题目标

找出代码中存在的真实缺陷（逻辑错误、边界遗漏、运行时异常、数据异常等），以用户视角描述触发场景和异常现象，让模型去定位并修复。

题目读起来像真实用户在反馈问题，而不是工程师在指派任务。

---

## 出题前置：bug 必须真实且可复现

**先读代码找 bug，再翻译成用户语言。不得反过来：不得先想一个合理的 bug 故事再套到项目上。**

出题前必须能在代码里同时指认清楚：

- 触发代码：文件名 + 行号 + 相关函数
- 观察点：用户在 UI 或接口返回上能直接看到的异常
- 最短复现步骤：用户从干净状态开始，几步操作能触发

硬性门槛：

- 最短复现步骤 > 3 步用户操作 → 换一个 bug；确实没有更短的，则在题目"触发场景"里把每一步都写全
- 复现依赖特殊前置状态（session 过期、脏 localStorage、特定角色数据、并发等）→ 前置动作必须写进题目，不得默认用户自己能想到
- bug 横跨多个文件/模块（例如某个视图看起来正常，真实根因在 store 清理或路由守卫里）→ 出题前必须通读完整调用链，不得只凭单个文件的表象就下笔

自问三遍，任何一条答不上来就重写题目：

1. 新克隆仓库、干净环境下，按题目步骤走一遍能不能看到题目描述的现象？
2. 题目里的"当前行为"是代码真实行为，还是我脑补的 bug 剧本？
3. 被测模型只看题目、不看我的分析，能不能定位到我心里选定的那段代码？

## 出题前置：找不到真实缺陷时的处理

- 默认批次里 `缺陷修复` 有 7 条配额；不要为了凑数量把"正常但不够好看"的实现写成缺陷。
- 如果连续换了 3 个切入点，仍然在代码里找不到可复现的真实缺陷，就把该编号改判为 `功能迭代`，并在工作簿备注里写明改判原因。
- 禁止编造仓库里不存在的报错、数据丢失或安全问题；宁可改判类型，也不要交一条对不上的题。

## 提示词质量标准

**必须包含：**
- 用户遇到了什么问题（异常现象、错误结果、功能失效）
- 触发该问题的操作路径或场景
- 期望的正确行为（对比当前错误行为）
- 至少一个连带面：同一根因影响的其它入口、其它数据类型或后续操作，是否也要一起正常

**禁止包含：**
- 文件路径、函数名、类名、变量名
- 数据库表名、字段名、API 路径字符串
- "修改 xxx 文件""调用 xxx 方法"等技术指令
- Markdown 格式（标题、粗体、列表符号、代码块）

## 难度下限：平台「过于简单」拒收口径

平台对难度有下限：**同一道题同时命中两项及以上「过于简单」特征时一律拒收**。
出这道题之前必须先按下表逐项自查，命中项必须压到 1 项以内，其中 `修改范围` 不允许命中。

| 特征 | 长什么样 | 典型写法 |
| --- | --- | --- |
| 修改范围 | 改动收在一处判断、一个文件或一段文案里 | 「顺序不对时直接给个提示」「把这段提示补全」 |
| 交互轮次 | 一次点击或一次提交就能验完，没有后续步骤、返回、刷新、切换 | 「点查询的时候提示一下就行」 |
| 技术广度 | 只落在一个技术面，通常只有输入校验，没有状态、数据、接口、并发、权限这些第二个面 | 「加一条时间先后校验」 |
| 逻辑复杂度 | 只有单一条件判断（顺序、空值、长度、格式、大小），没有复合条件或与其它业务规则的咬合 | 「判断开始时间是否晚于结束时间」 |
| 验证深度 | 只有开心路径，既没有非开心路径，也没有跨状态一致性要求 | 「正常查询不报错即可」 |

**下限动作，缺一项就要重出：**

- 至少压 2 个咬合的缺陷点，或 1 个共享根因在两个以上入口都能看到，不允许只描述一处异常。
- 至少牵动两个以上彼此相关的文件层级，例如页面入口、状态或数据流、共用校验、服务层、持久化、样式层。
- 操作时间线必须跨多轮：触发前 → 触发 → 结果落地 → 返回或刷新后再次进入 → 另一个入口再验一遍。
- 至少覆盖 2 类非开心路径（空数据、失败重试、边界输入、重复提交、并发时序、权限差异等）。
- 至少 1 项跨页面或跨状态一致性要求（刷新后保持、返回后恢复、列表与详情同步、多入口口径一致）。
- 至少包含一个校验之外的第二个技术面（状态与持久化、数据与接口、并发与时序、权限与角色、交互与呈现）。

**强制实测：**

- 把这条提示词写进临时文件后运行：
  `python3 /Users/fengyin/.codex/skills/solo-creater/scripts/check_prompt_difficulty.py --prompts-file "<临时文件>"`
- 返回 `ok: false` 时，说明至少命中两项「过于简单」特征，必须换切入点和主诉求重出，只加几个限定词不算重出。
- 脚本是词面兜底，返回 `ok: true` 也必须按上面的下限动作再自查一遍语义。

**难度要求：**

- 根因必须横跨两个以上彼此相关的文件层级，或横跨共用校验、状态清理、路由收尾这类共享链路，不得只落在单个组件的单处判断上。
- 现象必须在题面写出的操作路径上真实可见，并在修复后能说清哪一步不再复现。
- 如果一个切入点写出来只能是一处校验加一句提示，说明这个切入点本身过浅，必须换角度，不要靠加形容词拔高。

**隐藏约束：**
- 允许把"同一缺陷在其它入口也要一并修好""修复后既有数据仍能正常读取"这类合理预期留在题面之外，交由验收阶段核对。
- 不允许隐藏缺陷本身：触发场景、异常现象和期望结果必须写进题面。

**字数要求：**
- 全文不超过 250 字（空白字符不计入），约束要求融入正文，不得单独分行或加标签前缀

## 正确示例

用户在批量导入数据时，只要某一行格式有误，界面就直接报错中断，前面已经成功的行也一并回滚，而且没有提示说明是哪一行出错。期望的行为是跳过出错的行、保留已成功的数据，并在导入结束后汇总这次跳过了多少行，方便用户回到文件里对应位置修正；导入过程中出错时，列表页也要能看出这次导入没有生效。

轨迹回放的筛选和统计经常对不上：开始时间填得比结束时间晚时页面照样提示查询成功，返回的还是上一次的设备数据；从结果页返回筛选区重新查询，已选设备被清空；同一段时间在列表页和回放页显示的总时长也差了一段。期望时间顺序不合法时不要发起查询并说明哪一项有问题，查询报错或结果为空时保留已选设备和时间，刷新后筛选条件仍然保持，两个页面按同一段筛选得到的总时长要一致。

## 反面示例（禁止出现此类写法）

❌ 请修复 ImportService.java 中 batchImport() 方法的事务处理逻辑，当 validateRow() 返回 false 时应只 rollback 当前行而不是整个事务。

❌ 修复 user_controller.go 第 142 行的空指针问题。

❌ 轨迹回放里把开始时间填得比结束时间晚，点查询仍然提示查询成功，期望起止时间顺序不正确时直接给出提示并不发起查询，保留已经选择的设备与时间。

最后这一条是被平台打回的真实反例，它同时命中 3 项「过于简单」特征：修改范围只在一处校验里加提示、交互轮次只有点一次查询、技术广度只有时间顺序比较。这类"加一条校验 + 给一句提示"的写法一律不要交，宁可换切入点；同一个场景按上面的第二条正确示例改写，把连带入口、返回与刷新后的表现、失败与空结果一起写进题面，才是合格写法。

## 常见错误

1. 把文件名或方法名直接写进题目 → 删掉，改用业务描述
2. 题目过于笼统，没有现象描述 → 补充"什么操作 → 出现什么问题"
3. 超过 250 字 → 合并相似内容，保留核心现象、触发路径和期望结果
4. 使用 Markdown 格式 → 改为纯文本段落
5. 写成单点兜底题，例如"顺序不对时给个提示""空值时拦截一下" → 这就是平台拒收的「过于简单」写法，必须换成多入口、多轮次、跨状态的缺陷
6. 题目只覆盖开心路径，没有失败、空数据、返回或刷新后的表现 → 按难度下限补齐非开心路径和跨状态一致性要求
