# 代码重构任务执行手册

## 出题目标

找出代码中存在的设计问题（逻辑混乱、重复代码、函数过长、耦合过紧等），描述维护困难的用户感受，让模型在不改变外部行为的前提下对内部结构进行优化。

题目读起来像维护者在抱怨代码难以扩展，而不是技术评审报告。

- 重构目标必须在代码里真实存在：能指出重复的两处实现、能指出相互耦合的几处判断，不要只为凑数量提一条"可以更优雅"的题。
- 如果找不到真实的重构目标，换个切入点重找；始终找不到就改判为其它任务类型，并在工作簿备注里写明原因。

---

## 提示词质量标准

**必须包含：**
- 当前代码引发的问题感受（难以修改、容易出错、逻辑混乱等）
- 重构的目标方向（提升可读性、拆分职责、减少重复等）
- 强调不改变外部行为/保持向后兼容
- 至少两条会被这次重构影响的真实调用路径或数据形态，说明它们改完后都要保持同样结果。
- 至少一项既有行为的固定要求：已有数据、已有入口或既有输出格式保持不变。

**禁止包含：**
- 文件路径、类名、函数名
- 具体重构手法指令（"提取成 Strategy 模式""用 DI 替换 new"）
- Markdown 格式

**隐藏约束：**
- 允许把"改动后边界输入的表现要与改动前一致""重复调用不会产生额外副作用"这类合理预期留在题面之外，交由验收阶段核对。
- 不允许隐藏重构对象本身：哪个功能范围难维护、希望达到什么效果必须写进题面。

**字数要求：**
- 全文不超过 250 字（空白字符不计入），约束要求融入正文，不得单独分行或加标签前缀

---

## 正确示例

订单处理的核心逻辑越来越难维护，每新增一种订单类型都要在好几处判断里同步改动，改一处容易漏另一处。希望在不影响现有功能的前提下重构，让新增类型时只需要在一个地方修改；普通订单和加急订单这两条现有路径的处理结果、以及已有订单数据的历史展示都要保持一致。

## 常见错误

1. 直接指定重构模式或手法 → 只描述问题现象，让模型自行决定方案
2. 没有强调"不改变外部行为" → 加入"在不影响现有功能的前提下"
3. 改动范围太模糊（"整个模块都要重构"）→ 聚焦到一个具体痛点
4. 超过 250 字 → 删去技术背景，保留"问题现象 + 重构目标 + 行为不变范围"
